# プラン複雑度ゲート付き Haiku レビュー hook — 設計

日付: 2026-07-13
ステータス: 実装済み

## 目的

プランモードで作成した計画が一定の複雑度を超えたとき、ユーザーへの承認UI表示前に「会話文脈ゼロの読み手」= Haiku サブエージェントにレビューさせ、計画が暗黙的に前提としている知識・未定義の用語・曖昧な記述を洗い出して改訂させる。前提知識ゼロの読み手が実行できる計画 = 暗黙知が残っていない計画、という考え方の自動化。

## 構成要素

| ファイル | 役割 |
|---|---|
| `claude/hooks/plan-review.sh` | PreToolUse hook 本体（matcher: `ExitPlanMode`）。複雑度判定・マーカー検証・差し戻し |
| `claude/settings.json` | `hooks.PreToolUse` に `ExitPlanMode` エントリ |
| `link.sh` | `claude_files` に `hooks/plan-review.sh` を追加（`~/.claude/hooks/` へ symlink） |
| `~/.claude/plan-review-state/<プラン名>-<パスハッシュ12桁>.json` | 実行時生成。deny 回数・最終スコア（hook 自身のみが書く） |

## 動作フロー

```
ExitPlanMode 呼び出し
  → [plan-review.sh]
      ├─ jq/shasum 欠如・planFilePath 無し・ファイル無し → 通過（fail open）
      ├─ 複雑度スコア < 閾値 → 通過
      ├─ プランファイル末尾の承認マーカーのトークンが発行済みトークンと一致（またはハッシュが承認済み内容と一致） → 通過
      ├─ deny 累計 ≥ 3 → 警告して通過（バックストップ）
      └─ deny + レビュープロトコル注入
            STEP 1 REVIEW   : model: haiku のサブエージェントがプランファイルを
                              「文脈ゼロの実装者」として読み、(a)質問なしに実行不能な
                              ステップ (b)未定義の用語・パス・前提 (c)複数解釈可能な
                              記述 (d)完了条件の欠落 を severity 付きで列挙
            STEP 2 TRIAGE   : 指摘を「計画の欠陥」と「レビュアーの能力限界ノイズ」に選別
            STEP 3 REVISE   : プランファイルを改訂
            STEP 4 LOOP     : critical/major がゼロになるまで再レビュー（最大3ラウンド）
            STEP 5 MARK     : deny 時に発行されたトークンをマーカー行として追記
                              → ExitPlanMode 再実行 → 通過 → 承認UI
```

## 複雑度スコア

```
score = (非空行数 ÷ 10) + (ステップ数 × 2) + (ファイル言及数 × 1)
発動条件: score ≥ 15
```

- ステップ数 = 番号付きリスト行 + チェックボックス行
- ファイル言及数 = 拡張子付きパス風トークン（拡張子先頭は英字。バージョン番号 `4.5` 等は除外）のユニーク数。`.spec.` / `.test.` は実体ファイルと同一視し、論理ファイル単位で数える
- deny 理由にスコア内訳を出力するため、運用ログから閾値を調整できる

重みの根拠: 3シグナルを同じ桁に正規化した上で、「実装者が詰まり得る地点」を最も直接数えるステップに最大の単価を置いた。閾値 15 は過去プラン 29 件の実測分布に基づく（軽度=単発修正 ≈9〜15 / 中度=1機能 ≈19〜34 / 重め=複数レイヤー ≈34〜87）。プランモードに入る時点で軽微な作業は除外されているため、実測ではプランファイルの約97%が対象になる。これは「プランモードを使うほどの作業はほぼ全部レビューする」という運用意図に対応する。

チューニング（環境変数）: `PLAN_REVIEW_THRESHOLD`（既定 15）/ `PLAN_REVIEW_MAX_DENIES`（既定 3）/ `PLAN_REVIEW_MAX_ROUNDS`（既定 3）/ `PLAN_REVIEW_STATE_DIR`

## 承認記録 = ワンタイムトークンのマーカー行

deny 時に hook がワンタイムトークンを発行し、deny 理由に埋め込む。エージェントはレビュー完了後、それをプランファイル末尾にマーカー行として書き写すだけでよい:

```
<!-- plan-review:approved token=t<deny回数>-<deny時内容ハッシュ先頭8桁> rounds=N -->
```

deny への対応中、セッションはまだプランモード内にあり、無許可で書き込めるのは**プランファイルのみ**（シェルコマンドは許可プロンプトが出る）。そのため承認記録はプランファイルへの追記で行い、エージェントにはハッシュ計算などのシェル実行を一切要求しない。照合ロジックはすべて hook 側:

1. 状態ファイルの `approved_hash` が現在の内容（マーカー行除外）のハッシュと一致 → 通過
2. マーカーのトークンが発行済みトークンと一致 → トークンを消費（単回使用）し、deny 回数を 0 にリセットし、現在の内容ハッシュを `approved_hash` / `last_content_hash` に記録して通過
3. どちらでもない → 新トークンを発行して deny（このとき deny 回数は、状態ファイルの `last_content_hash` が現在の内容ハッシュと異なる＝新しいレビューサイクルなら 0 から数え直し、同じなら加算する）

これにより、承認後に計画を編集すると自動的に再レビュー対象になり（ハッシュ不一致・トークン消費済み）、ユーザーが承認UIで No → 計画改訂のケースも正しく再判定される。複数マーカーが残っても最後の行のみ評価される。また deny 回数は内容ハッシュ単位でリセットされる（＝プラン内容が変わるたびに、または承認が記録されるたびに 0 から数え直す）ため、`MAX_DENIES` 到達によるバックストップは同一内容に対する繰り返し deny のみで発生し、レビューが恒久的にスキップされることはない。状態ファイル名にはプラン絶対パスのハッシュを含めるため、同名（basename）だが別パスのプランファイル間で状態が混線しない。

## 検証結果

### Phase 0（実地検証、2026-07-13）

- `PreToolUse` は matcher `ExitPlanMode` で発火する（公式ドキュメント未記載だが実測で確認。`PermissionRequest` も直後に発火）
- stdin の `tool_input` に `plan`（計画全文）と `planFilePath`（プランファイルの絶対パス）が含まれる
- hook は承認UI表示より前に実行される
- ヘッドレス（`claude -p`）のプランモードには ExitPlanMode ツールが存在しないため、検証は expect による対話セッション自動操縦で実施

### 単体テスト（13件 PASS）

短いプラン素通し / 複雑プラン deny / スコア内訳出力 / プロトコル注入 / バックストップ（3 deny 後に警告付き通過）/ 発行トークンで通過 / 承認済み内容の再実行も通過 / 承認後の編集で再 deny / 新トークン再発行 / 新トークンで再承認 / 閾値の環境変数上書き / planFilePath 欠如時 fail open / spec・test の対の論理ファイル正規化

### e2e（expect による対話セッション自動操縦、閾値=1）

全ステージ成功: deny（承認UI表示前）→ Haiku サブエージェントによるレビュー（2ラウンド）→ 計画改訂 → トークンマーカー追記 → ExitPlanMode 再実行 → 通過 → 承認UI到達。許可プロンプトによる中断なし。

補足: エージェント自身にハッシュを計算させる方式は成立しない（シェルコマンドが許可プロンプトで停止することを e2e で確認）。トークン方式が必須。

## 既知の制限

- hook 設定はセッション開始時に読み込まれるため、導入前から起動中のセッションには適用されない（要再起動）
- レビューを実施するのはメインエージェント（deny 理由のプロトコルに従う）。従わない場合でもバックストップにより 3 deny 後に通過するため、デッドロックはしない
- マーカーは承認UIに表示される計画本文の末尾に HTML コメントとして見える
- スコアは表層的な指標（行数・ステップ・ファイル数）であり、意味的な複雑さは測らない
