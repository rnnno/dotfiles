# bestof

best-of-N で複数案を生成し、前提を懐疑役に検証させ、judge に選定させるスキル。

入力は会話の文脈から読み取る（`/bestof` で明示された指定があればそれを優先）: 検討したい仕様・課題、案の数（省略時3・上限5）、判断基準（省略時は文脈から提案して確認を取る）。

**先に確認すること**: これはトークンコストが N+2 倍になる重い操作。今回の判断が「軽微」なら使わず通常のフローで進めることをユーザーに提案する。ユーザーが明示的に望む場合のみ以下を実行する。

## 手順

1. **仕様・案の数・判断基準を確定する。**
   会話の文脈から検討対象の仕様/課題を読み取り、一文に要約して提示する。案の数は指定が無ければ3、上限5。判断基準（各基準の重要である理由と、あれば重み）が指定されていなければ、文脈から妥当な基準を提案し、**実行前にユーザーに確認する**（基準が結果を決めるため、ここを勝手に決めない）。
   判断基準には「前提の正しさ（手順3で成立が確認できた事実に基づいているか）」を**必ず1項目として含める**。`judge` は判断基準に無い評価軸を持ち込まない設計のため、この項目が無いと前提の破綻を減点に反映できない。

2. **候補を並列生成する。**
   案の数だけ、独立したサブエージェント（`general-purpose` など）を**1メッセージで並列**に起動する。各エージェントには仕様だけを渡し、**他の候補は見せない**（独立性の確保）。各エージェントには「中心となる仮説を1行で述べた上で、具体的な案を出す」ことを指示する。

3. **各案の現状認識を懐疑役に検証させる。**
   サブエージェントを1つ起動し、全候補が前提としている現状（存在するテーブル・カラム、実装済みの機能、対象ブランチとベースブランチの差）を独立に検証させる。渡すのは仕様と全候補の記述のみで、**どの案を推すかは指示しない**。file:line または実際のコマンド出力を根拠として、成立する前提／成立しない前提／確認できなかった前提に分類して返させる。全候補が同じ誤った前提に立っている場合はここでしか気づけないため、省略しない。

4. **judge サブエージェントに判定させる。**
   `judge` を1つ起動し、判断基準（各基準の理由と、あれば重み）と全候補（A/B/C… とラベル付けし、**要約せず全文**）、および手順3の前提検証結果を渡す。judge には候補生成に関与していないことが前提。成立しない前提に依存した案は、手順1で入れた「前提の正しさ」の基準に照らして減点理由として明示させる。

5. **結果を報告する。**
   judge が返した「結論・選定理由・勝者の弱点（必須）・敗案からの移植推奨」をそのまま提示する。成立しない前提・未確認の前提が残っている場合は併記する。

6. **採用は別ステップ。**
   このスキルは判定までで終わる。勝者案を実際に採用・実装するかはユーザーの判断を待つ（自動で反映しない）。
