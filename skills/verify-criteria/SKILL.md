# verify-criteria

現在の計画の進行状況に対して、独立検証（verifier）を実行するスキル。

対象は会話の文脈から読み取る（ユーザーがサブタスクを指定していればそれを使う）。

## 手順

1. **対象サブタスクと完了条件を特定する。**
   - ユーザーが対象を指定していればそれを使う。指定が無ければ、直近でユーザーまたは自分が「完了した」と述べたサブタスクを対象にする。
   - 完了条件と検証手段を次の順で探す。
     1. アクティブな計画ファイル（`~/.claude/plans/` 配下）。見出しは `## 完了条件` / `## 完了条件（検証）` / `## 検証（完了条件）` のいずれか（表記は揺れる）。
     2. 計画ファイルが無ければ、着手前に提示した完了条件を会話から拾う。
     3. どちらも無ければ、そのタスクの完了条件を1〜5項目に起草し、AskUserQuestion で一度に確認を取る。「見つからないので確認します」だけで終わらせない。
   - 完了条件が計画全体にしか書かれていない場合（通常こうなる）は、対象サブタスクに関係する項目だけを抜き出す。関係する項目が1つも無ければ、その旨を明示して検証不要として終了する。

2. **verifier サブエージェントを起動する。**
   渡すのは以下の4点だけ。実装の経緯・進捗ログ・「こう直したので通るはず」といった説明は渡さない（後付け正当化を防ぐため）。

   ```
   対象: <サブタスク名（識別のみ）>
   作業ディレクトリ: <対象リポジトリ/ディレクトリの絶対パス>
   完了条件:
   - <条件1>
   検証手段:
   - <コマンドまたは確認方法>
   ```

   計画に検証手段が明示されていない場合は、完了条件から自分で導出して埋める（空欄で渡さない。verifier が照合手段を失う）。

3. **判定を報告する。**
   verifier が返した3値判定（機械照合OK / 機械照合NG / 目視要）と総合判定（PASS / PASS（目視要あり） / FAIL）をそのまま提示する。

4. **FAIL の場合は再検証する。**
   - NG になった項目を修正する。verifier は読み取り専用なので、修正は必ず自分で行う。
   - 修正後は手順2に戻って verifier を再起動する（スキル全体をやり直さない）。再検証は完了条件の全項目で行う（NG 項目だけに絞らない。修正が他項目を壊している可能性があるため）。
   - 報告には毎回「検証 n 回目」と明記する。同一サブタスクで**通算3回 FAIL** した場合はループを止め、残っている NG 項目とその根拠を提示して「再計画が必要」とユーザーに伝える（パッチの繰り返しで押し切らない）。

5. **目視要が残る場合は、完了扱いにしない。**
   - 「PASS（目視要あり）」は完了ではなく**人間確認待ち**として報告する。「PASS」だけを取り出して完了と書かない。
   - 目視要の原因が「検証手段を渡していなかった」ことにある場合は、検証手段を補って手順2から再検証する。人間に投げる前に機械照合を試みる。
   - 原理的に機械照合できない項目だけを残項目として列挙し、何を人間が確認すべきかを書いてユーザーに確認を仰ぐ。黙って完了と報告しない。
