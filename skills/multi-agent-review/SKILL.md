# Multi-Agent Review（多観点レビュー）

レビュー観点を洗い出すサブエージェントと、観点ごとにレビューするサブエージェントを使い、変更を多観点で並列レビューしてサマリーを返すスキル。オーケストレーション（観点の集約・固定観点の付与・並列起動・結果集約）は **main（このスキルを実行しているあなた）** が行う。

このスキルは **report-only**。指摘の自動修正は行わない。

## レビューの狙いと除外方針

このスキルが拾うのは、**放置すると実害があるもの**と、**適用するとコードが減るもの**だけ。指摘が増えること自体に価値は無い。

### 拾うもの

**壊れる・危険**
- セキュリティ（認証・認可の欠落、機微情報の露出、インジェクション、信頼できない入力の到達）
- 実行すればエラーになる／誤った結果を返すコード
- 想定できていないエッジケース（空・0件・上限超過・null・順序・重複・タイムゾーン・並行・失敗時の状態）
- 既存の握りつぶし（すでに catch している箇所が例外を飲み込み、障害が見えない／不整合が残る）
- リソース・後始末漏れ（コネクション／ファイル／トランザクションの未クローズ、購読解除漏れ）

**無駄が残る・実は動いていない**
- 消し忘れ・デッドコード（デバッグ出力、コメントアウトされた旧実装、到達しない分岐、使われない引数・import、一時回避コードの残骸）
- 既存実装の重複（同等の関数・ユーティリティが既にあるのに新規追加している）
- 検証していないテスト（アサーション無し、常に真になる assert、モックしすぎて本体を通っていない、skip 放置）
- スコープ外の変更混入（無関係なファイルの変更、意図しない削除・巻き戻し）

**依頼との不一致**
- タスク説明が渡されている場合、要求された挙動になっていない／変更漏れがある

### 出さないもの

- 到達経路を示せない入力へのバリデーション追加
- 根拠のないタイムアウト・リトライ・サーキットブレーカーの付与
- 例外を捕まえてログを出すだけの `try/catch` の追加
- 防御的な null / 型チェックの網羅
- 「念のため」のログ・コメント・アサーションの追加
- 動作を変えないリファクタ提案（責務分割、抽象化の見直し、命名の改善）
- 実害を示さない「〜した方がよい」提案

**例外（基準4のみ）**: 周囲の既存実装が一貫してその書き方をしている場合に限り、逸脱元の `file:line` を添えて基準4として出してよい。リポジトリ内に逸脱元を示せないものは該当しない。

### 判定基準

指摘は次の**いずれかを満たすもののみ**採用する:

1. **失敗シナリオを書ける** — どの入力・状態で、何が壊れるか（到達経路つき）
2. **適用するとコードが減る** — 削除・統合・既存実装への置換
3. **依頼された仕様と食い違っている**
4. **既存実装との具体的な不一致** — 逸脱元となる既存コードの `file:line` を添えられるもの（固定観点で使う。リポジトリ内に根拠が無い一般論のベストプラクティスは該当しない）

禁じているのは**トピックではなく、失敗シナリオの無い一般論**。エラー処理・バリデーション・タイムアウトの指摘も、基準1を満たすなら通常どおり採用する。

main は 手順2・手順4 でサブエージェントを起動する際、**この節の内容をそのままプロンプトに含める**。

## 手順

### 1. レビュー対象の特定

- 引数や会話で対象（ファイル/作業内容）が**明示されていればそれを使う**。
- 明示が無ければ既定で**ブランチ差分**を取得する。base ブランチは upstream → develop → main の順でフォールバック検出する:

  ```bash
  BASE=$(git rev-parse --abbrev-ref @{upstream} 2>/dev/null | sed 's|origin/||' \
    || (git rev-parse --verify origin/develop >/dev/null 2>&1 && echo develop) \
    || echo main)
  git diff origin/$BASE...HEAD --name-only
  ```

- ブランチ差分が空なら、未コミット差分にフォールバック（`git diff --name-only` / `git diff --cached --name-only`）。
- それも空なら、**中断**してユーザーに「レビュー対象が見つからない。対象を指定してほしい」と伝える。
- あわせて、**この変更が何を実現しようとしているか**を会話・タスク説明・PR 本文から 1〜3 行にまとめる（「依頼との不一致」を見るために必要）。判断材料が無ければ「不明」と明記し、そのままサブエージェントへ渡す（推測で埋めない）。
- 確定した**差分範囲**（例 `origin/develop-vn...HEAD`）と**変更ファイル一覧**を要約してユーザーに提示する。

### 2. レビュー観点の洗い出し（finder を1つ起動）

`review-perspective-finder` サブエージェントを **1つ** 起動する。プロンプトに以下を渡す:

- 差分範囲（または対象ファイル一覧）
- 変更ファイル一覧
- 「レビューの狙いと除外方針」節の内容
- 手順1でまとめたタスクの説明（無ければ「不明」）

finder は自分でコードを読み、観点リスト（各観点 = `title` / `rationale` / `focus`）を返す。
※ finder には「スタイル/規約準拠の観点は含めない」ことが指示済み（手順3で main が付与するため）。

### 3. 固定観点の追加（main が必ず付与）

finder が返した観点リストに、main が**必ず次の1観点を追加**する:

> **既存コードの書き方・パターン・命名・スタイルに従っているか**
> - rationale: 周囲の既存実装と一貫し、保守性を損なわないことを担保する。
> - focus: 変更ファイル全体と、近接する既存の同種実装・`CLAUDE.md` の規約。

この観点は**既存コードとの不一致**を見るためのもので、一般論としてのベストプラクティス（防御的コーディング、教科書的な設計原則）は対象外。

これで「finder 由来の観点」＋「固定観点1つ」が最終的な観点リストになる。
finder が観点ゼロを返した場合は、この固定観点1つだけでレビューを行う。

### 4. 観点ごとに並列レビュー（perspective-reviewer を観点数だけ起動）

最終観点リストの**数だけ** `perspective-reviewer` サブエージェントを起動する。観点数の**上限は設けない**。

- **1つのメッセージ内で複数の Agent 呼び出しをまとめて発行**し、並列実行させる。
- 各エージェントのプロンプトには、その**担当観点1つ**（title / rationale / focus）、**レビュー対象**（差分範囲・対象ファイル一覧）、**「レビューの狙いと除外方針」節の内容**、**タスクの説明**を渡す。
- 各エージェントは担当観点だけに集中して findings（severity 付き）を返す。

### 5. main による取捨判断（対応要否の仕分け）

サブエージェントは差分しか見ていないが、**main は実装の背景・意図・会話の文脈を知っている**。その知識を使い、集約した各指摘を「対応すべきか」で仕分けする:

- **要対応**: 実害があり、修正・確認が必要な指摘。
- **対応不要**: 背景を踏まえると問題にならない指摘（例: 意図的な設計、既存仕様、別箇所で担保済み、スコープ外、誤検知）。

判断は背景知識に基づいて行い、**指摘を黙って捨てない**。対応不要にしたものは必ず理由を残す（後でユーザーが妥当性を判断できるように）。

あわせて、**「出さないもの」に該当する指摘がすり抜けていたら、背景を問わず「対応不要」へ落とす**（理由は「冗長化系のため除外」）。「判定基準」の1〜4をどれも満たさない指摘も同様に扱う。
ただし**「出さないもの」の例外**（周囲の既存実装との不一致で、逸脱元の `file:line` が添えられているもの）はこの対象外で、通常どおり要否を判断する。

### 6. サマリー報告（main）

- **要対応サマリー**（メイン）: 観点ごとにセクションを分け、severity（🔴critical / 🟠high / 🟡medium / 🟢low）付きで並べる。冒頭にレビュー対象・観点数・重大度別の件数を置く。
- **対応不要**: 全件を列挙しない。**件数と除外理由カテゴリの内訳を1行**で出す（例: `対応不要: 3件（バリデーション追加2 / 命名提案1）`）。続けて「詳細が必要なら言ってください」の一行を添える。仕分けの根拠は手元に保持し、求められたら出す。
- いずれかの reviewer が失敗・未完了なら「**N/M 観点完了**」と明示する（取りこぼしを黙って隠さない）。
- report-only。修正は行わない（ユーザーが望めば別途対応する）。

## 原則

- オーケストレーション（観点集約・固定観点付与・並列起動・結果集約）は main が担う。サブエージェントは「観点を出す」「1観点でレビューする」に専念させる。
- finder・reviewer はいずれも read-only。このスキルの実行中にファイルを編集しない。
- 観点数に上限はないが、`perspective-reviewer` は必ず**1メッセージで並列起動**してレイテンシを抑える。
- **指摘ゼロは正常な結果**。件数を埋めるために「出さないもの」を混ぜない。
